# How the Guardian's agents work

The Guardian finds supply-chain risks with deterministic scanners, then uses **seven agents** to decide which
risks matter for *this* application, how urgently, and how to fix them. The system is **neurosymbolic**:

- **Neural:** LLM agents investigate, using read-only tools, and propose verdicts, facts and fixes.
- **Symbolic:** a fact store, a rule set and a verifier decide what is allowed and check every agent answer.
  A rule engine sets the final priority.

No agent can change code, approve a fix, or invent a fact. Every agent has a rule-based fallback, so the whole
pipeline also runs with no API key.

---

## Pipeline at a glance

```
scan (deterministic)                       findings.json, sbom, dependency graph
  │
analyze
  ├─ technical score per risk               analyze/prioritize.py
  ├─ 5 Business Context agent + rules       analyze/business.py      → business_context.json
  ├─ 1 Lead: route cases                    agents/orchestrator.py
  ├─ 2 Vulnerability Analyst ┐ in parallel
  ├─ 3 Supply-Chain Forensics┘
  ├─ 1 Lead: triage (score ±20)
  ├─ 4 Critic: second opinion on P1 cases
  └─ 6 Neurosymbolic Prioritizer            neurosymbolic/prioritizer.py → final score, priority, confidence, why
  │
plan      7 Remediation Planner + 4 Critic on the whole plan
approve   human, bound to the plan's SHA-256 hash
apply     sandbox git branch only
validate  rebuild + rescan; 7 Remediation Planner proposes the next iteration
report    guardian_report.html / .txt / .json
pr        the approved, validated fix as a pull request on the scanned GitHub repository (after a final "y")
```

## Shared machinery

### One agent engine (`agents/base.py`)
Every agent runs the same loop. Each turn the model replies with exactly one JSON object:

```json
{"tool": "<name>", "args": {...}, "why": "..."}     // run a read-only tool
{"final": {...}}                                     // the agent's answer
```

- An agent may only call the tools on **its own list**. Any other tool name returns an error to the model.
- The case and every tool result get an **evidence id** (`E1`, `E2`, …). Answers must cite them in `evidence_refs`.
- Each agent has a **step limit** (1 to 5). If it runs out, or the LLM is unavailable, the rule fallback answers.
- Providers: Claude → Gemini → local Ollama (`qwen3:4b` by default, no key, no rate limit) → rules.
  Groq is used only when chosen with `LLM_PROVIDER=groq`. You can give one agent its own model, e.g.
  `CRITIC_PROVIDER=gemini` or `VULNERABILITY_ANALYST_MODEL=...` in `.env`.

### Fact store (`neurosymbolic/facts.py`)
The only place agents get facts from. Sources: the scan (findings, dependency paths, SBOM), the repository itself
(imports, file lines), and public read-only data (OSV advisories, npm/PyPI versions, deps.dev dependency trees,
EPSS, CISA KEV). Nothing in it is generated by a model.

### Tools (`agents/tools.py`)
All tools are read-only queries on the fact store.

| Tool | Returns |
|---|---|
| `item_details` | the risk, its findings, evidence and technical score |
| `dependency_paths` | how the package enters the app, direct parents, dev-only |
| `code_usage(package)` | where the app imports it (`file:line`) |
| `advisory(vuln_id)` | advisory summary, affected ranges, fixed versions |
| `exploit_intel` | EPSS and CISA KEV for the risk's CVEs |
| `registry_info(package, version)` | npm metadata: source repo, maintainers, publisher, install scripts |
| `registry_versions(package)` | published versions |
| `compare_downloads(package, other)` | weekly downloads of two packages (typosquat check) |
| `baseline_change` | what changed for this package since the previous scan |
| `file_lines(file, line)` / `read_lines` | lines of a repository file |
| `dependency_tree(package, version)` | resolved tree of a published version (deps.dev) |
| `safe_upgrade(package)` | smallest version ≥ the fix whose own tree has no known CVE |
| `list_files`, `search_repo(text)` | find files and lines in the repository |

### Hard rules (`neurosymbolic/rules.py`)
Limits no agent can override:
- allowed verdicts (`confirmed_risk`, `likely_false_positive`, `needs_human_review`)
- the 9 allow-listed fix types and their required parameters
- the Lead may move a score by at most **±20**
- confidence below **0.6** sends a case to human review
- priority bands: **P1 ≥ 80, P2 ≥ 60, P3 ≥ 35, P4 below**

### Verifier (`neurosymbolic/verifier.py`)
Every agent answer comes out **accepted**, **corrected** (fixed by a rule, with a note) or **rejected** (the rule
fallback is used instead). It checks:
- cited evidence ids exist; with no valid citation, confidence is capped at 0.3
- a CVE mentioned must appear in the gathered evidence
- a `file:line` mentioned must exist
- a target version must exist in the registry and be ≥ the advisory's fixed version
- a remediation action must be allow-listed, with all required parameters, and its manifests must exist
- score changes stay within ±20, and every change has a reason

## The seven agents

### 1. Orchestrator & Triage (Lead)
Plays two roles, each a single LLM call with no tools.

**Routing.** Receives the cases chosen for investigation: the **top 6** by technical score plus up to **3** extra
high or critical supply-chain cases (categories 1.3, 1.4, 1.6). It decides which specialist investigates each case
and which cases the Critic reviews.
- *Verifier:* CVE cases (1.1, 1.2) must reach the Vulnerability Analyst; all others reach Forensics; every P1 case
  gets the Critic. Anything missing is added.
- *Fallback:* route by category; send every P1 to the Critic.

**Triage.** After the specialists answer, it sets a score for every case at once, moving the technical score by at
most ±20 with a reason. It also writes a 3–4 sentence summary for engineering leads.
- *Verifier:* clamps moves beyond ±20; reverts a move with no reason; recomputes the band from the score.
- *Fallback:* −20 if every specialist judged it a likely false positive; +5 if one confirmed it is exploitable here.

### 2. Vulnerability Analyst
**Question:** is this known CVE exploitable in *this* application?
Checks how the package enters the app, whether the app imports it, what the advisory says, exploitation
intelligence, and a safe target version.
- *Tools (≤5 steps):* `item_details`, `dependency_paths`, `code_usage`, `advisory`, `exploit_intel`,
  `registry_versions`, `safe_upgrade`
- *Answer:* verdict, exploitable in context (yes/no/unknown), risk summary, recommended action, target version,
  confidence, evidence, reasoning.
- *Fallback:* `likely_false_positive` if dev-only and unreachable; otherwise `confirmed_risk` for P1/P2 and
  `needs_human_review` below. Exploitable is "yes" if the package is loaded.

### 3. Supply-Chain Forensics
**Question:** is this artifact trustworthy, and where did it come from?
Handles non-CVE risks: look-alike or starjacked packages, install scripts, lockfile and registry tampering,
container images, CI/CD workflows. Compares registry metadata, maintainers, downloads, the actual script or file
lines, and what changed since the last scan.
- *Tools (≤5 steps):* `item_details`, `dependency_paths`, `registry_info`, `registry_versions`,
  `compare_downloads`, `code_usage`, `baseline_change`, `file_lines`
- *Answer and fallback:* same format and rules as the Vulnerability Analyst; the fallback action is replace
  (look-alike), pin (container or CI), block (tampered) or upgrade.

### 4. Critic / Reviewer
An independent second opinion, run twice:
- **In `analyze`:** on every P1 case and every case the Lead flagged. It looks for wrong reachability assumptions,
  false-positive typosquats and missing evidence. A disagreement sends the case to the **human review queue**.
- **In `plan`:** on the whole remediation plan. It looks for a fix that keeps or introduces a vulnerable
  dependency, or a major upgrade that may break the app.
- *Tools (≤3 steps):* `item_details`, `code_usage`, `advisory`, `registry_info`, `dependency_tree`
- *Rule:* it may only disagree with a concrete reason. Reviews of case ids that don't exist are dropped.
- *Fallback:* agrees, but flags major-version upgrades and escalations for a second look.
- Tip: `CRITIC_PROVIDER=gemini` gives it a different model family from the specialists.

### 5. Business Context
**Question:** what does the application do for the business?
It establishes, **per project** (manifest), whether the project serves network traffic and which sensitive data
it handles (credentials, payment, personal, auth tokens).
1. **Pattern rules always run first.** Server code (`.listen(`, `express()`, `Flask(__name__)`, `EXPOSE 3000`, …)
   means internet-facing; keywords (password, card number, email, jwt, …) mean the matching data class. Each
   fact records the `file:line` that matched.
2. **The agent adds facts the rules missed.** Tools: `list_files`, `search_repo`, `read_lines` (≤5 steps).
3. **Its facts are verified.** One is kept only if the cited line exists and actually shows that data.
4. **A person can confirm or reject each fact** with `python -m guardian business <repo>`. Rejected facts are
   ignored from then on.

Its facts feed a small SSVC-style bonus on the technical score (Act +15 … Track 0) and the business-loss
dimension of agent 6.

### 6. Neurosymbolic Prioritizer
Turns everything above into the final priority. It has **no LLM**: its inputs include the agents' verified
outputs, and a rule file decides.
- **Inputs:** scan facts (CVSS, KEV, EPSS, reachability, dependency paths, scanner agreement), the outputs of
  agents 1–5, and human decisions from `guardian review`.
- **Rules:** `config/neurosymbolic_rules.json` scores five dimensions (threat, production use, business loss,
  supply-chain integrity, blast radius), applies hard gates, and computes a confidence.
- **Output per risk:** score 0–100, P1–P4, confidence (high/medium/low), a one-line "why", and a full reasoning
  list built from the rules that fired, so it can't invent a reason.
- **Evidence rule:** a specialist's verdict only counts when a **model** produced it, the verifier accepted it,
  and its confidence is ≥ 0.6. Rule fallbacks only restate the scan, so counting them would double-count it.
- A low-confidence P1/P2, or an unconfirmed look-alike package, goes to the human review queue.

See [PRIORITIZATION.txt](PRIORITIZATION.txt) for every rule and a worked example.

### 7. Remediation Planner
Works on the **re-prioritised** list (P1 and P2, plus high supply-chain risks).
- **In `plan`:** the rule-based planner proposes an allow-listed fix for each risk. The agent may keep it or improve
  it, e.g. upgrade a parent instead of overriding a child, or pick a version whose own dependency tree is clean.
  - *Allowed actions:* `npm_upgrade_direct`, `npm_override_transitive`, `npm_replace`, `npm_remove`,
    `pypi_upgrade`, `docker_pin_digest`, `action_pin_sha`, `block`, `escalate`
  - *Tools (≤4 steps):* `item_details`, `dependency_paths`, `registry_versions`, `dependency_tree`,
    `safe_upgrade`, `code_usage`
  - *Verifier:* rejects non-allow-listed actions, missing parameters, versions that don't exist or are below the
    fix, and unknown manifests. `block` actions are fixed by policy and never changed.
- **In `validate`:** when a finding remains after the fix, it proposes the next step, usually upgrading the parent
  that still pulls in the vulnerable package.

The plan is then hashed (SHA-256). A human must approve that exact hash before `apply` changes anything, and only
in a sandbox branch.

## Where a human is involved

| Command | Purpose |
|---|---|
| `python -m guardian business <repo>` | confirm or reject business facts |
| `python -m guardian review <repo>` | decide cases the agents disagree on or are unsure about (confirm / dismiss) |
| `python -m guardian approve <repo> [--web]` | approve the remediation plan (bound to its hash) |

Review decisions never apply changes. Agent 6 reads them on the next `analyze`: a dismissal moves the risk to P4,
and a confirmation keeps it at P2 or higher.

## Where to see the results

- `runs/<repo>/analysis.txt`: priorities, explanations and every agent's case file
- `runs/<repo>/guardian.html`: dashboard. Click a package for the prioritizer's score, confidence and reasoning,
  then each agent's steps and verifier notes.
- `runs/<repo>/guardian_report.html`: the end-to-end story per fix: finding → evidence → agents → action →
  approval → result
- `runs/<repo>/audit.jsonl`: every stage, LLM call (provider and model, never keys), approval and change
